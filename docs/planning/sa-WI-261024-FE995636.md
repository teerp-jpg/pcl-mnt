## 4. Workflow และสถานะ
### 4.1 งานซ่อม (maintenance_record)
DRAFT → IN_PROGRESS → COMPLETED
DRAFT → COMPLETED (บันทึกย้อนหลังงานที่เสร็จแล้ว ต้องผ่านเงื่อนไข COMPLETED ครบ)
DRAFT / IN_PROGRESS → CANCELLED
COMPLETED → แก้ได้ผ่าน correction เท่านั้น (ต้องใส่เหตุผล + บันทึก audit)
- DRAFT: กรอกไม่ครบได้ ไม่นับในรายงาน
- IN_PROGRESS: ต้องมี vehicle, ประเภท, วันที่เข้าซ่อม
- COMPLETED: ต้องมีวันที่เสร็จ, อู่, รายการอย่างน้อย 1 บรรทัด, เลขไมล์ (ถ้าไม่มีต้องใส่ odometer_missing_reason) นับในรายงาน ถ้าเป็น PM ที่ผูกแผนไว้ จะรีเซ็ตรอบของแผนนั้น
- CANCELLED: ต้องใส่เหตุผล ไม่นับในรายงาน
### 4.2 รถ (vehicle.status)
ACTIVE ↔ INACTIVE → DISPOSED (ต้องมี disposed_at) — เปลี่ยนสถานะได้ทั้งจากการนำเข้า CSV และจากการแก้ใน MNT
### 4.3 จุดต่อขยายสำหรับการอนุมัติในอนาคต (D4)
- ทำ state machine เป็นตารางการเปลี่ยนสถานะใน domain service ที่เดียว (dict ของ from → set[to]) ห้ามเขียน if กระจายหลายที่
- enum สถานะเก็บใน PostgreSQL เป็น text + CHECK constraint (ไม่ใช้ native ENUM) เพื่อให้ migration เพิ่ม PENDING_APPROVAL ได้ง่าย
- ตอนเปลี่ยนสถานะให้ส่ง event ภายใน (`record_status_changed`) เพื่อให้ workflow อนุมัติมาเกาะได้ภายหลัง
- เฟส 1 ห้ามมีสถานะหรือ API ของการอนุมัติ

## 5. ทะเบียนรถและการเชื่อมกับ CORE (D1)
### 5.1 หลักการ
- ช่วงแรก MNT ถือข้อมูลรถไว้เป็นสำเนาที่แก้ไขได้ ตั้งต้นจาก CSV ของ CORE
- เพิ่ม/แก้รถใน MNT ได้ทันที แล้วระบบจดลงคิวว่าต้องส่งไป CORE
- ส่งไป CORE ด้วยไฟล์ CSV ที่ระบบสร้างให้ ผู้ดูแล CORE นำเข้าเอง (MNT ไม่เขียนเข้า CORE)
- เก็บแค่ฟิลด์ที่จำเป็นให้น้อยที่สุดตามที่ผู้ใช้ต้องการ
### 5.2 Template CSV สำหรับนำเข้า (UTF-8 มี/ไม่มี BOM ก็ได้, คั่นด้วย comma, แถวแรกเป็น header)
| คอลัมน์ | บังคับ | หมายเหตุ |
|---|---|---|
| core_asset_id | ใช่ (สำหรับไฟล์จาก CORE) | คีย์สำหรับจับคู่ |
| plate_no | ใช่ | ตัดช่องว่างหัวท้าย และเก็บค่า normalized ไว้ค้นหา (ตัดช่องว่าง/ขีด) |
| province | ใช่ | |
| vehicle_type | ไม่ | เช่น หัวลาก, 6 ล้อ, กระบะ |
| brand, model | ไม่ | |
| year | ไม่ | ค.ศ. 4 หลัก ถ้าปีมากกว่า 2400 ถือเป็น พ.ศ. แล้วแปลง |
| chassis_no | ไม่ | ถ้ามีต้องไม่ซ้ำ |
| status | ไม่ | ACTIVE/INACTIVE/DISPOSED ค่าเริ่มต้น ACTIVE |
| disposed_at | ถ้า status=DISPOSED | YYYY-MM-DD |
- ถ้าชื่อคอลัมน์ของ CORE ไม่ตรงกับนี้ ให้ปรับที่ dict mapping ใน config (`CORE_CSV_COLUMN_MAP`) ไม่ต้องแก้โค้ดส่วน logic
- ขนาดไฟล์ไม่เกิน 5 MB / 10,000 แถว
### 5.3 ขั้นตอนนำเข้า (2 ขั้น: ตรวจ → ยืนยัน)
1. อัปโหลด → สร้าง vehicle_import_batch สถานะ VALIDATED พร้อมผลตรวจรายแถว: NEW / UPDATE / UNCHANGED / CONFLICT / ERROR
2. ผู้ใช้ดูผลตรวจ แล้วกดยืนยัน → นำแถว NEW/UPDATE ลงทั้งหมดใน transaction เดียว สถานะเป็น APPLIED แถว ERROR/CONFLICT ไม่นำลง
3. นำเข้าไฟล์เดิมซ้ำ (sha256 ตรงกัน) → เตือน แต่ไม่บล็อก ผลจะออกมาเป็น UNCHANGED ทุกแถว (idempotent)
4. รถที่มีใน MNT แต่ไม่มีในไฟล์ → ไม่ลบและไม่เปลี่ยนสถานะ (ไฟล์อาจมีไม่ครบ) แค่แสดงในรายงานผลว่า "ไม่พบในไฟล์"
### 5.4 กฎการจับคู่และข้อมูลชนกัน (ค่าเริ่มต้นที่ SA เสนอ)
- จับคู่ด้วย core_asset_id ก่อน ถ้าไม่เจอ ให้ลองจับคู่ plate_no+province กับรถที่เพิ่มใน MNT และยังไม่มี core_asset_id → ถ้าเจอคันเดียว ผลเป็น CONFLICT (ต้องให้คนกด "ผูกกับคันนี้" ระบบไม่ผูกเอง) ถ้าไม่เจอ ผลเป็น NEW
- ถ้ารถคันนั้นมีการแก้ใน MNT ที่ยังไม่ได้ส่ง CORE (core_sync_status ≠ SYNCED) และไฟล์มีค่าต่างจาก MNT → ผลเป็น CONFLICT ห้ามทับ ผู้ใช้เลือกได้รายแถวว่า "ใช้ค่าจาก CORE" หรือ "คงค่า MNT"
- ถ้าไม่มีการแก้ค้าง → ใช้ค่าจาก CORE ทับ (UPDATE) และ audit เก็บค่าก่อน/หลัง
- plate_no+province ซ้ำกับรถ ACTIVE คันอื่น หรือ chassis_no ซ้ำ → ERROR
- ถ้าทะเบียนเปลี่ยน → เพิ่มแถวใน vehicle_plate_history
### 5.5 เพิ่ม/แก้รถใน MNT และส่งกลับ CORE
- เพิ่มรถใหม่: core_asset_id ว่าง, origin=MNT, core_sync_status=PENDING_CREATE
- แก้รถที่มาจาก CORE: core_sync_status=PENDING_UPDATE และเก็บรายการฟิลด์ที่เปลี่ยนใน vehicle_change (before/after)
- ส่งออก: GET /vehicles/core-export สร้าง CSV ของรถที่ค้างอยู่ (คอลัมน์ตาม 5.2 + mnt_vehicle_id + change_type CREATE/UPDATE + changed_fields) แล้วบันทึก core_export_batch ไว้ รถในไฟล์เปลี่ยนสถานะเป็น EXPORTED
- เมื่อ CORE นำเข้าแล้ว: ทางที่ 1 นำเข้า CSV ของ CORE รอบถัดไปที่มี core_asset_id ของรถใหม่ (จับคู่ตาม 5.4 แล้วผูกรหัสให้) ทางที่ 2 ผู้ใช้กรอก core_asset_id เองแล้วกด "ยืนยันว่า CORE รับแล้ว" → SYNCED
- สถานะ: SYNCED → PENDING_CREATE/PENDING_UPDATE → EXPORTED → SYNCED (ถ้าแก้อีกตอน EXPORTED ให้กลับเป็น PENDING_*)
### 5.6 จุดต่อขยายเฟส 2
- interface `CoreAssetSource` (Protocol): `iter_assets() -> Iterator[CoreAssetRow]` ให้ CSV importer ทำตาม interface นี้ เฟส 2 ค่อยเพิ่มตัวที่ดึงจาก API ได้โดยไม่แก้ logic จับคู่ใน 5.4
- interface `CoreChangeSink`: เฟส 1 คือ CSV exporter

## 6. กฎธุรกิจและข้อยกเว้น
BR-01 ทุกงานผูกกับรถ 1 คัน (vehicle_id) และเก็บ plate_no_snapshot/province_snapshot ตอนสร้างงาน
BR-02 maintenance_type ต้องเป็น PM หรือ CM เท่านั้น
BR-03 วันที่เข้าซ่อมต้องไม่เกินวันนี้ (Asia/Bangkok) และวันที่เสร็จต้องไม่ก่อนวันที่เข้าซ่อม
BR-04 เงินใช้ Decimal / NUMERIC(14,2) สกุล THB ห้ามใช้ float โดย amount ของแต่ละบรรทัด = qty × unit_price ปัด ROUND_HALF_UP เป็น 2 ตำแหน่ง subtotal = ผลรวม amount และ vat_amount ให้กรอกเอง (ตามใบแจ้งหนี้ ≥ 0) total = subtotal + vat_amount คำนวณฝั่ง server เสมอ
BR-05 qty > 0 และ unit_price ≥ 0 ถ้า unit_price = 0 ต้องติ๊ก is_warranty หรือใส่หมายเหตุ
BR-06 เลขไมล์ต้องไม่น้อยกว่าค่าล่าสุดก่อนหน้าตามวันที่ ถ้าน้อยกว่าต้องใส่ odometer_regression_reason
BR-07 งาน PM ผูก pm_plan ได้ (ต้องเป็นรถคันเดียวกัน) เมื่อ COMPLETED ให้ตั้ง last_done_at = service_end_date และ last_done_km = odometer_km ของแผนนั้น
BR-08 งาน CM ต้องมี failure_description
BR-09 รถคันเดียวกัน + อู่เดียวกัน + invoice_no ซ้ำกับงานที่ไม่ CANCELLED → เตือนว่าอาจบันทึกซ้ำ (ไม่บล็อก ต้องกดยืนยัน)
BR-10 แก้งาน COMPLETED ต้องใส่ correction_reason และ audit เก็บค่าก่อน/หลัง
BR-11 สถานะ PM: OK / DUE_SOON (เหลือไม่ถึง 10% ของรอบ หรือ ≤ 500 กม. หรือ ≤ 14 วัน ปรับได้ใน system_setting) / OVERDUE ถ้ามีหลายเงื่อนไขให้ใช้อันที่ถึงก่อน ถ้าไม่มีเลขไมล์ล่าสุดให้ดูแค่เงื่อนไขวัน
BR-12 รถ DISPOSED: ดูประวัติได้ แต่สร้างงานที่วันที่เข้าซ่อมหลัง disposed_at ไม่ได้ (ASSET_DISPOSED) ส่วนรถ INACTIVE สร้างงานได้แต่มีคำเตือน
BR-13 plate_no+province ต้องไม่ซ้ำในรถที่ไม่ใช่ DISPOSED และ chassis_no ต้องไม่ซ้ำถ้ามีค่า
BR-14 ห้ามลบรถที่มีงานซ่อมแล้ว (ให้เปลี่ยนสถานะแทน) ส่วนรถที่ยังไม่มีงานลบได้เฉพาะตอนยัง PENDING_CREATE
BR-15 อู่ที่ is_active=false เลือกในงานใหม่ไม่ได้ แต่งานเก่ายังแสดงชื่อเดิม ชื่ออู่ห้ามซ้ำ (เทียบแบบไม่สนตัวพิมพ์/ช่องว่าง) ส่วน tax_id ถ้ามีต้องเป็นตัวเลข 13 หลักและไม่ซ้ำ

## 8. Data model (PostgreSQL 17, SQLAlchemy 2.0, Alembic; timestamp เป็น timestamptz; สถานะเป็น text + CHECK)
- vehicle: id uuid PK, core_asset_id text UNIQUE NULL, plate_no, plate_no_norm, province, vehicle_type, brand, model, year smallint, chassis_no UNIQUE NULL, status, disposed_at date NULL, origin (CORE_IMPORT/MNT), core_sync_status (SYNCED/PENDING_CREATE/PENDING_UPDATE/EXPORTED), last_imported_at, created_*/updated_*, version
  partial unique: (plate_no_norm, province) WHERE status <> 'DISPOSED'
- vehicle_plate_history: id, vehicle_id FK, plate_no, plate_no_norm, province, valid_from, valid_to NULL, source (CORE_IMPORT/MNT)
- vehicle_change: id, vehicle_id, change_type (CREATE/UPDATE), before_json, after_json, changed_by, changed_at, export_batch_id NULL

## 12. Acceptance criteria
AC-01 นำเข้า CSV ตาม 5.2 แล้วได้ผลตรวจรายแถวถูกต้อง (NEW/UPDATE/UNCHANGED/CONFLICT/ERROR) และ apply แล้วข้อมูลลงครบใน transaction เดียว ถ้าล้มต้อง rollback ทั้งหมด
AC-02 นำเข้าไฟล์เดิมซ้ำแล้วไม่มีข้อมูลเปลี่ยน และได้คำเตือน IMPORT_FILE_SEEN_BEFORE
AC-03 ไฟล์ CORE ห้ามทับค่าที่แก้ใน MNT แล้วยังไม่ sync (ต้องเป็น CONFLICT) และ apply ไม่ได้ถ้ายังมี CONFLICT ที่ไม่ได้เลือก resolution (IMPORT_UNRESOLVED_CONFLICT)
AC-04 รถที่เพิ่ม/แก้ใน MNT ต้องโผล่ใน core-export CSV พร้อม change_type ถูกต้อง และสถานะไหลตาม 5.5
AC-05 ทะเบียนเปลี่ยนแล้ว งานเก่ายังแสดง plate_no_snapshot เดิม และค้นได้ทั้งทะเบียนเก่าและใหม่
AC-06 สร้าง/ปิดงาน PM/CM ได้เมื่อผ่าน BR-03…BR-08 ถ้าไม่ผ่านได้รหัส error ตามส่วนที่ 9 และ maintenance_type อื่นนอกจาก PM/CM ได้ 422
AC-07 ยอดเงินคำนวณที่ server ทุกครั้ง ค่า total ที่ client ส่งมาไม่ถูกใช้ ทดสอบตามตัวอย่างปัดเศษในส่วนที่ 11
AC-08 เปลี่ยนสถานะนอก workflow ส่วนที่ 4.1 ได้ 409 INVALID_STATE_TRANSITION และใน API/DB ไม่มีสถานะอนุมัติ
AC-09 correction งาน COMPLETED โดยไม่มีเหตุผลได้ 422 ถ้ามีเหตุผลต้องมี audit ก่อน/หลัง
AC-10 ปิด PM ที่ผูกแผนแล้ว /pm-due คำนวณรอบใหม่ตามตัวอย่าง และ DUE_SOON/OVERDUE ตาม BR-11
AC-11 สร้างงานกับรถ DISPOSED หลัง disposed_at ได้ ASSET_DISPOSED
AC-12 PATCH ด้วย version เก่าได้ 409 VERSION_CONFLICT
AC-13 รายงาน CSV ต้องตรงกับผลรวมใน DB ของงาน COMPLETED เท่านั้น
AC-14 สิทธิ์ตามตารางส่วนที่ 7: viewer เรียก POST/PATCH ได้ 403, clerk นำเข้า CSV/cancel ได้ 403 และทุก role เห็นรถทุกคัน
AC-15 อู่ที่ปิดใช้งานเลือกในงานใหม่ไม่ได้ แต่งานเก่ายังแสดงชื่อ
AC-16 Frontend ผ่าน `tsc --noEmit` แบบ strict ไม่มี any; backend มี pytest ครอบคลุม BR-01…BR-15 และกฎนำเข้า 5.3/5.4; Alembic upgrade/downgrade รันบน PostgreSQL 17 ว่างได้
